## Эксперимент с очередями выполнения

Прогноз я записал до запуска `npm run example:order`.

| Этап | Порядок меток | Объяснение |
|---|---|---|
| Прогноз до запуска | A, B, C, D, E, F | Сначала весь синхронный код (A, B, C), потом микрозадачи (D, E), потом таймер (F). |
| Фактический результат | A, B, C, D, E, F | Совпал с прогнозом. |

Фактический вывод:

```text
A: синхронный код
B: начало async-функции
C: конец синхронного кода
D: обработчик Promise
E: продолжение после await
F: задача таймера
```

Объяснение:

- **Синхронный код:** A, B, C. Метка B тоже синхронная: тело `async`-функции выполняется обычным образом до первого `await`. Дальше функция «засыпает», и управление возвращается наружу, поэтому C выводится сразу после B.
- **Микрозадачи:** D и E. Обработчик `.then()` (D) был поставлен в очередь раньше, чем продолжение после `await null` (E), поэтому D идёт перед E.
- **Таймер:** `setTimeout(..., 0)` не вызывается сразу. Он ставит задачу в очередь задач, а она выполняется только после того, как закончатся текущий код и все микрозадачи. Поэтому F последняя.
- **Что будет, если удалить один обработчик Promise:** оставшиеся метки не поменяют порядок относительно друг друга. Пропадёт только удалённая метка (например, без D порядок станет A, B, C, E, F).

### Свой обработчик (пункт 6 задания)

Я добавил в `examples/event-loop.js` ещё один обработчик (метка G). Он стоит в коде после вызова `demonstrateAwait()`, то есть позже, чем D и продолжение E.

| Этап | Порядок меток |
|---|---|
| Прогноз | A, B, C, D, E, G, F |

## Организация кода

| Файл | Ответственность |
|---|---|
| `api/server.mjs` | готовый учебный сервер (не менялся) |
| `src/api-client.js` | общий HTTP-клиент: сборка URL, `fetch`, проверка статуса и `Content-Type`, JSON, тайм-аут, отмена, класс `ApiError`. Ничего не знает про задачи |
| `src/task-api.js` | знает маршруты `/tasks` и `/categories`, проверяет фильтры и схему данных, умеет грузить задачи и категории параллельно |
| `src/variant.js` | только данные варианта: номер и фильтры |
| `src/main.js` | консольный сценарий: вызывает `loadInitialData` и печатает результат |

**Почему `fetchFn` передаётся в `createApiClient`.** Так в модульных проверках можно подставить поддельный `fetch` и проверить клиент без сети: вернуть заранее заготовленный `Response`, выбросить ошибку или «зависнуть» для проверки тайм-аута. Реальный `fetch` используется по умолчанию.

**Почему HTTP-ошибки проверяются отдельно от сетевых.** Это разные ситуации. Сетевая ошибка — ответа нет совсем (`fetch` отклоняет Promise). HTTP-ошибка — сервер ответил статусом 4xx/5xx. Если всё поместить в один `try`, то `ApiError` с видом `http`, созданный после `fetch`, попадёт в тот же `catch` и будет ошибочно назван `network`. Поэтому в `try` стоит только вызов `fetchFn`.

**Почему JSON проверяется по контракту.** Корректный синтаксис JSON не гарантирует нужную структуру. Например, `{"data":"не массив"}` — валидный JSON, но с ним нельзя работать как со списком задач. Поэтому `task-api.js` проверяет поля, типы, уникальность `id` и `meta.total`.

## Реализация общего клиента

| Требование | Как реализовано | Проверка |
|---|---|---|
| Нормализация `baseUrl` | функция `parseBaseUrl`: `new URL(baseUrl)`, проверка `http`/`https`, запрет `query` и `hash`; при сборке пути слеши по краям обрезаются регулярным выражением | проверки 01, 04 |
| Кодирование query | `url.searchParams.append(name, String(value))`; пропускаются только `undefined`, `null`, `""`, поэтому `false` и `0` сохраняются; входной объект не меняется | проверки 02, 03, С1 |
| Заголовок `Accept` | `headers: { Accept: "application/json" }`, метод `GET` | проверка 05 |
| Проверка `response.ok` | после получения `Response`: `if (!response.ok) throw await createHttpError(...)` | проверки 08, 09, 16 |
| Проверка `Content-Type` | регулярное выражение на `application/json` (и `+json`), проверка идёт до `response.json()` | проверки 10, integration 11 |
| Разбор JSON | `await response.json()` в отдельном `try`; `SyntaxError` сохраняется как `cause` | проверка 11, integration 10 |
| Ограничение времени | `AbortSignal.timeout(timeoutMs)` передаётся в `fetch` | проверка 14, integration 12 |
| Внешняя отмена | `AbortSignal.any([signal, timeoutSignal])`; по `combinedSignal.reason` отличаем тайм-аут от отмены | проверка 15, integration 13, С6, С7 |

Порядок работы `requestJson`: проверка `timeoutMs` → `buildUrl` → сигналы → `try { fetchFn }` → проверка, что вернулся `Response` → `!ok` → `204` → `Content-Type` → `response.json()`.

## Доменный модуль задач

Фактические результаты (реальный API):

| Вызов | Результат |
|---|---|
| `getTasks()` | 12 задач, id: 1, 4, 7, 10, 13, 16, 19, 22, 25, 28, 31, 34 |
| `getTasks({ completed: false, priority: "high" })` | 3 задачи, id: 4, 13, 34 |
| `getTaskById(25)` | `{ id: 25, title: "Исправить обработку ошибок", completed: true, priority: "high", categoryId: 2 }` |
| `getCategories()` | 1 «Учёба», 2 «Проект», 3 «Организация» |
| `loadInitialData({ q: "провер" })` | `{ tasks: [id 7, 16], categories: [3 шт.], meta: { total: 2, filters: { ..., q: "провер" } } }` |

Правила проверки:

- **Задача:** `id` — положительное безопасное целое; `title` — строка, после `trim` от 1 до 100 символов; `completed` — boolean; `priority` — `low`, `medium` или `high`; `categoryId` — положительное безопасное целое.
- **Категория:** `id` — положительное безопасное целое; `name` — строка, после `trim` от 1 до 100 символов.
- **Уникальность:** в `data` не должно быть одинаковых `id` (проверяется через `Set`).
- **`meta.total`:** должен быть равен `data.length`. Также `data` обязано быть массивом, а `meta.filters` для задач — объектом.
- **Фильтры (до запроса):** разрешены только `completed` (boolean), `priority`, `categoryId` (целое > 0), `q` (строка до 100 символов, пробелы по краям обрезаются). Всё остальное — `TypeError`, запрос не отправляется.
- Любая ошибка схемы превращается в `ApiError` с `kind: "invalid-response"`.

## Последовательная и параллельная загрузка

Временный эксперимент `npm run experiment:parallel`: два запроса к `/debug/delay?ms=200`, по три запуска каждого варианта.

| Сценарий | Запуск 1, мс | Запуск 2, мс | Запуск 3, мс | Наблюдение |
|---|---:|---:|---:|---|
| Два последовательных `await` | 447 | 405 | 410 | время ≈ сумме двух задержек (2 × 200 мс) |
| `Promise.all` | 205 | 204 | 205 | время ≈ одной задержке (200 мс) |

Вывод: при последовательном варианте второй запрос не начинается, пока не придёт ответ на первый, поэтому время складывается. При `Promise.all` оба запроса уже отправлены до ожидания, и сервер обрабатывает их одновременно, поэтому ждём примерно дольше из двух. Цифры зависят от компьютера и сравнивать их с чужими не нужно. В итоговый код (`loadInitialData`) искусственные задержки не входят.

## Вывод

Я реализовал общий HTTP-клиент (`api-client.js`) и модуль для работы с задачами (`task-api.js`). Все три набора проверок проходят: 18, 26 и 13 успешных, ошибок нет. Дополнительно написаны и проходят 8 собственных проверок. Вариант 7 даёт задачи с id `[7, 16]`, `meta.total = 2`.

Что нужно различать:

- **Ожидание Promise.** `fetch` возвращает Promise, а не данные. Результат появляется позже, поэтому нужен `await`; код после вызова успевает выполниться раньше.
- **HTTP-ошибка (`http`).** Сервер ответил, но статус не 2xx (404, 400, 503). `fetch` при этом не отклоняется, поэтому статус проверяется через `response.ok`. Из тела берутся `code`, `message`, `details`.
- **Сетевая ошибка (`network`).** Ответа нет вообще, например сервер остановлен. Тут `fetch` отклоняет Promise.
- **Неверный ответ сервера (`invalid-response`).** Статус успешный, но `Content-Type` не JSON, JSON повреждён или структура не подходит под схему.
- **Тайм-аут (`timeout`).** Ответ не пришёл за заданное время; запрос прерывается сигналом `AbortSignal.timeout`.
- **Явная отмена (`aborted`).** Запрос отменил вызывающий код через `AbortController`.

Главные ошибки, которых надо избегать: один общий `try` на всё (HTTP-ошибка становится «сетевой»), отбрасывание `false` при сборке query и последовательные `await` для независимых запросов. Также запомнить: `Promise.all` сам по себе запросы не отменяет — при отказе одного из них остальные продолжают выполняться.
